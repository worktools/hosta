# Hosta / Hoya core-path review — 2026-09-08

Baseline: Hosta main `a7e7a92` (PR #18 merged). Scope: CLI request/error handling,
HTTP dispatch/authentication, deployment/invocation/retry, engine protocol,
JSON persistence, datasource/scheduler paths and read-only workspace. Hoya v1
protocol, process isolation and runtime limits were inspected read-only. This is
a targeted code review, not a complete security audit or performance benchmark.

## Findings fixed in this change

| Priority | Finding and effect | Resolution |
| --- | --- | --- |
| P1 | `executor.ts` assigned the complete engine response into a run. Unknown engine fields could overwrite Hosta-owned IDs, version, input or deployment context. | Engine client returns an explicit protocol-field allowlist. Regression injects control-plane overrides. |
| P2 | Null engine responses, invalid log timestamps and incomplete errors escaped validation, yielding generic platform failures during result handling. | Validate response object, log fields/timestamps, nonnegative duration and complete error shape; report `ENGINE_PROTOCOL`. Capability arrays are checked explicitly. |
| P2 | Route-specific catches converted malformed JSON into 500; null management payloads could cause TypeErrors; idempotency changed error semantics. Oversized requests risked socket destruction before a 413 response. | Parse management writes once before dispatch/idempotency, require object envelopes, preserve 400/413 for invoke parsing and keep the stream available for the response. Guest execution inputs retain JSON scalar/array support. |
| P2 | Unknown API GET routes fell through to SPA HTML with HTTP 200, confusing agents. | Reserved API/invocation paths return JSON 404; normal SPA fallback remains. URL parsing uses a fixed base instead of the Host header. |

## Follow-up backlog

- **P1 / #10: persistence and restart recovery.** `save()` serializes writes but
  mutations happen before persistence and are not rolled back on failure. A
  restart loads `running` records without reconciling them. Define unknown-outcome
  semantics, add fault-injection tests and transactional storage before claiming
  durable execution recovery. Do not automatically replay side effects.
- **P1 / #10: bounded external datasource requests.** The test endpoint in
  `src/routes/datasource.ts` uses unrestricted `fetch()` plus `.text()` without a
  deadline/byte cap. A slow or oversized upstream can retain resources. Add
  deadline, streaming cap, redirect/credential policy and structured errors.
- **P2 / #12: scheduler failure handling.** The timer callback awaits execute/save
  without a rejection handler; storage failure can escape the timer. Define
  missed-run and persistence-failure semantics and test restart/failure paths.
- **P2 / #6: discovery accuracy.** `src/routes/apps.ts` still advertises `ctx.call`
  in discovery while Hoya v1 intentionally does not support guest network/inter-app
  I/O. Reconcile generated invocation docs and `/llms.txt` with supported commands.

## Verified boundaries and limits

Hoya's default v1 mode uses per-execution child processes, four admission slots,
wall-clock timeout, artifact correlation and bounded worker output. Legacy routes
are selected separately with `HOYA_MODE=legacy-demo`; no claim is made that legacy
mode has the same isolation guarantees. No Hoya source changes are included.

The workspace cancels stale reads and fetches run details on demand. Run queries
retain one page plus lookahead, but historical storage and filtered scans still
grow with record count. This review does not claim indexed or multi-process scale.

Validation: production build and full Hosta tests using the real local Hoya binary,
including JS/Rust WASM lifecycle, engine protocol failures, HTTP malformed/null/
oversized input, idempotency consistency and JSON 404. Test artifacts stay in
ignored build directories or temporary directories.
