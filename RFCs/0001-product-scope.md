# RFC 0001：产品边界与 MVP

> 2026-09-06：范围、独立引擎边界和交付顺序按 [RFC 0013](0013-independent-engine-platform.md) 修订；本文保留历史决策，不代表当前实现状态。

- 状态：Accepted for planning
- 日期：2026-08-04

## 1. 背景

Hosta 希望把“描述一个需求”缩短为“获得一个可调用的小服务”。长期形态包括定时/事件触发、服务发现、工作流编排、根据运行反馈优化代码、成本监控和脚本市场，但这些能力同时建设会让产品价值无法尽早验证。

MVP 先回答一个问题：普通用户能否在网页里描述一个小型自动化，获得经过一次真实试运行、随后可通过 Webhook 调用的服务？

## 2. 目标用户和首个场景

目标用户是会描述业务规则、但不一定能独立部署服务的个人或小团队。

首版适合：

- JSON 数据转换、筛选、聚合和格式化；
- 调用一个获准的 HTTP API，再整理响应；
- 接收 Webhook，执行短时逻辑并返回 JSON。

首版不适合：长任务、浏览器自动化、任意系统命令、文件持久化、需要完整 npm 生态的应用，以及高风险生产业务。

## 3. MVP 用户故事

1. 用户在网页输入自然语言需求，并可补充一份示例 JSON 输入。
2. AI 生成结构化需求、JavaScript 代码、输入 schema 和简短说明。
3. 系统在沙箱内用示例输入执行代码，展示返回值、日志、耗时和错误。
4. 用户可以追加修改要求，系统生成新版本并再次试运行。
5. 用户确认后发布该版本，得到稳定的 HTTP Webhook 地址和调用密钥。
6. 用户通过网页或 HTTP 调用服务，并查看每次运行的状态和日志。
7. 用户可以停用服务；已发布版本不因草稿生成而自动变化。

## 4. MVP 范围

### 必须包含

- 单用户或本地管理员模式；
- Web UI：创建、生成状态、代码/说明、试运行、发布、调用记录；
- DeepSeek 文本模型接入；
- JavaScript 生成和受限执行；
- 手动试运行和 HTTP Webhook 两种触发方式；
- 版本不可变，发布指针可切换；
- 超时、输出大小、日志大小和并发限制；
- 模型调用与脚本执行的基本耗时、token/估算成本记录；
- 敏感配置从服务端注入，绝不写入生成代码或模型上下文。

### 明确不做

- 多节点调度和云端自动扩缩容；
- cron、消息总线和第三方事件连接器；
- 多步骤可视化工作流；
- 系统依据日志自动修改并自动发布代码；
- npm 包安装、Python 和原生二进制；
- 团队协作、计费、市场和公开分享；
- 将 LLM 生成结果未经验证直接部署。

这些能力均可后续加入，但不能阻塞 MVP 主流程。

## 5. 核心产品原则

- **版本先于应用**：每次生成产生不可变版本；应用只是草稿版本和已发布版本的指针。
- **试运行先于发布**：只有至少一次成功试运行的版本可以发布。
- **能力显式授予**：脚本默认无网络、文件和环境变量访问；需要的能力在应用配置中声明。
- **AI 是建议者**：MVP 允许 AI 生成和修订，但发布由用户显式确认。
- **失败可理解**：模型失败、校验失败、运行失败和平台失败使用不同状态与错误码。

## 6. 成功指标

- 典型 JSON 转换需求从提交到首次成功试运行不超过 60 秒（不含模型供应商异常）。
- 新用户无需命令行即可完成创建、试运行、发布和网页内调用。
- 发布版本可以通过文档化的 `curl` 示例稳定调用。
- 任何失败运行均能在 UI 中关联到应用、版本、触发来源和日志。
- 生成失败或新版本失败不会影响已发布版本。

## 7. 后续阶段

- Phase 2：定时任务、事件连接器、受控 secrets、PostgreSQL、队列与独立 worker。
- Phase 3：可视化 DAG、服务目录、脚本间带权限调用、人工审批节点。
- Phase 4：基于指标提出优化建议；必须经过测试和审批后发布。
- Phase 5：模板/脚本市场、多租户治理与计费。
