# RFC 0011：LLM 生成代码执行沙箱——业界方案综述与 Hosta 定位

- 状态：Informational（背景调研，非实现决策；结论用于指导未来架构演进）
- 日期：2026-08-12
- 相关代码：[`src/executor.ts`](../src/executor.ts)、[`src/validator.ts`](../src/validator.ts)、[`src/wasm-bridge.ts`](../src/wasm-bridge.ts)、[`RFC 0002`](0002-mvp-architecture.md)
- 关联项目：[`hoya`](../../hoya)（独立的 Rust 执行引擎，QuickJS + Wasmtime）

## 1. 背景与目的

Hosta 的核心场景是"LLM 生成代码 → 立即执行验证 → 发布为可调用服务"，因此**如何安全执行不受信任的、机器生成的代码**是平台级风险点。业界针对"运行 LLM/Agent 生成或调用的代码"已经形成了几类成熟技术路线，本 RFC 系统整理这些方案的原理、优劣、成本模型与适用场景（含中国大陆云厂商与开源方案），并对照 Hosta 当前实现（`vm.createContext` + WASM/JSPI）与关联项目 `hoya`（QuickJS + Wasmtime）给出定位判断，为后续是否需要升级隔离方案提供依据。

本 RFC **不改变**任何现有实现，仅作调研记录。

## 2. 隔离边界的分层视角

评价一个沙箱方案，本质是问："不受信任的代码和宿主之间隔了几层边界？每层边界能挡住什么攻击面？" 从弱到强大致可分六层：

```text
① 语言层黑名单        —— 同进程同堆，靠字符串/AST 规则禁止危险 API，无真实边界
② 独立解释器/字节码 VM —— 同进程不同"世界"，宿主能力需显式注入，无隐式全局对象
③ Isolate / WASM 能力模型 —— 同进程独立内存空间 + capability-based，需显式导入宿主函数
④ OS 级容器/命名空间   —— 独立文件系统、PID/网络 namespace，共享内核
⑤ MicroVM/独立内核     —— 独立虚拟化内核，硬件级隔离
⑥ TEE/机密计算         —— 独立于宿主 OS/Hypervisor 的硬件可信根，不信任宿主只信任 CPU
```

层级越高，隔离越强，但冷启动时间、资源开销、工程复杂度也随之上升；⑥级是一条与①-⑤正交的信任模型（防的是"宿主本身被攻破"而非"沙箱内代码逃逸"），成本也通常最高。业界方案基本都能归到这六层之一或组合体。

## 3. 各类方案详解

### 3.1 语言层黑名单沙箱（① 级）

**代表**：Node.js `vm.createContext` / `vm.runInContext`、Python `exec()` + `RestrictedPython`、`Function` 构造器沙箱。

- **原理**：在同一进程、同一 V8/CPython 实例内创建一个"看起来隔离"的全局对象，配合正则/AST 黑名单拒绝 `require`、`process`、`eval` 等危险标识符。
- **优点**：零依赖、启动几乎无开销（微秒级）、实现简单。
- **缺点**：**不是真正的安全边界**。Node.js 官方文档明确警告 `vm` 模块 "is not a security mechanism"——已有大量公开的逃逸技巧（如通过 `constructor.constructor` 拿到未沙箱化的 `Function`，或利用 `Proxy`/`Reflect` 污染宿主原型链）。黑名单枚举永远追不上绕过手法。
- **成本**：边际成本几乎为零，不需要额外基础设施、不产生网络往返，只有一次性的黑名单编写/维护工时。隐性成本是安全事故的尾部风险——一旦规则被绕过，损失上限等于宿主进程能触达的一切（数据、密钥、其他租户数据），这部分风险无法用云账单衡量，只能靠额外的运行时监控/审计成本去缓释。
- **适用场景**：单用户本地工具、代码在生成后仍由开发者本人审阅才发布、不直接暴露给公网匿名用户。**不适合多租户 SaaS**。
- **Hosta 现状**：`validator.ts` 中 JS 校验正是这一类——正则拒绝 `require|process|globalThis|eval|Function` 等关键字，执行走 `vm.createContext`（见 [`executor.ts`](../src/executor.ts)）。这是当前 MVP 阶段的合理取舍（详见第 5 节）。

### 3.2 独立解释器嵌入（② 级）

**代表**：QuickJS（及 Rust 绑定 `rquickjs`/`quickjs-wasm-rs`）、Boa（Rust 实现的 JS 引擎）、Goja（Go 实现的 JS 引擎）、Deno `core`（基于 V8 但去除了几乎所有全局能力）。

- **原理**：不复用宿主自己的运行时（不是同一个 Node/V8 实例），而是在进程内嵌入一个**从零构建、默认无任何宿主能力**的独立解释器。`fetch`、文件系统、网络等能力必须由宿主显式注册为 host function 才存在，不存在"忘记拉黑一个 API"的问题——因为默认就是空白画布。
- **优点**：攻击面天然小（没有 `process`/`require` 可言，因为解释器压根不认识这些概念）；QuickJS 体积小（~1MB）、启动快（毫秒级）；适合"每次调用起一个新 Runtime"的一次性沙箱模式。
- **缺点**：仍然和宿主进程共享同一操作系统进程/内存空间/文件描述符表；没有 CPU/内存的硬限额（QuickJS 有中断回调可做超时，但内存无上限）；死循环/内存膨胀仍可能拖垮宿主进程（需要额外用线程+超时 kill 兜底）。
- **成本**：基础设施成本很低，嵌入式解释器体积通常在 1-5MB 量级，不需要容器镜像仓库或编排系统；主要成本是一次性的宿主能力桥接开发（为每个 host function 写绑定代码）。若自建服务器承载，边际成本约等于 CPU 时间加服务器折旧，没有为每次执行创建独立环境（容器/VM）的固定开销，因此在高并发短任务场景下单位调用成本通常是几类方案里最低的一档。
- **适用场景**：需要频繁短时执行、又不想承担容器/VM 冷启动成本的场景；作为"比 vm.createContext 更彻底"的中间方案。
- **代表落地**：`hoya` 项目的 `execute_js`（[`src/js_engine/mod.rs`](../../hoya/src/js_engine/mod.rs)）正是用 `rquickjs::Runtime` + `Context::full` 执行远程脚本，宿主能力通过 `register_to_globals_with_capture` 显式挂载。

### 3.3 V8 Isolate 多租户隔离（②-③ 级之间）

**代表**：Cloudflare Workers（V8 Isolates）、Deno Deploy、Fastly Compute@Edge（早期）。

- **原理**：仍是同进程内的 V8，但每个租户拥有独立的 `Isolate`（独立堆、独立 GC），比 `vm.createContext`（同 Isolate 内的多 Context）隔离性更强，并配合平台层的 CPU 时间片配额、内存硬限额（超限直接 kill Isolate）。
- **优点**：冷启动极快（<5ms）、单机可承载数千租户、成本低；配合 CPU/内存配额可以做到"资源耗尽只影响自己"。
- **缺点**：仍共享内核与进程，理论攻击面比容器/VM 大；对可执行的宿主 API 集合有限制（Workers 不能访问任意文件系统）；自建需要较深的 V8 embedding 经验，一般公司自研成本高，更多是"用别人的平台"（Cloudflare/Deno）而非自建。
- **成本**：自建门槛极高（相当于自研一个 V8 embedding 平台，通常是数十人月的专家工时），因此绝大多数使用者选择按量付费使用现成平台——按请求数加 CPU 时间计费（而非按整机时长），由于冷启动趋近于零、资源利用率高，同等负载下单价通常明显低于容器/MicroVM 方案；代价是被单一平台锁定（vendor lock-in），迁移成本高。
- **适用场景**：边缘计算、API 网关级别的用户自定义逻辑（webhook transform、中间件）。

### 3.4 WebAssembly + Capability 模型（③ 级）

**代表**：Wasmtime、Wasmer、WAMR，配合 WASI 或自定义 import object；浏览器/Node 内置 `WebAssembly` API。

- **原理**：WASM 天生是**能力安全（capability-based security）**模型——WASM 模块默认不能访问任何宿主资源（文件、网络、时钟），唯一与外界交互的方式是宿主显式注入的 import 函数。即使 WASM 代码本身是恶意的，它拿不到未被显式授权的能力，这是**语言规范层面**的安全边界，而不是运行时打的补丁。
- **优点**：安全边界最"干净"——不存在需要枚举黑名单的问题，只需要审查宿主注入了哪些 import；线性内存与宿主堆物理隔离，天然防止指针越界攻击宿主对象；多语言编译目标（Rust/C/Go/MoonBit/AssemblyScript 等）。
- **缺点**：需要工具链把目标语言编译到 wasm32（并非所有语言/库都能顺利编译，尤其依赖动态特性或系统调用的库）；异步宿主能力需要 JSPI 或 Asyncify 等桥接机制，心智负担较高（见 [RFC 0010](0010-wasm-jspi-error-handling.md)）；同样没有内置 CPU/内存硬限额（Wasmtime 可配置 `fuel`/内存 page 上限，但需要显式配置，默认未必开启）。
- **成本**：一次性工程成本主要在工具链适配（把目标语言编译到 wasm32、处理异步桥接），一旦编译产物就绪，运行时成本与嵌入式解释器相当——进程内执行、无需独立环境，边际成本主要是 CPU/内存；相比容器/MicroVM，没有镜像存储、网络 namespace 等额外开销，是"证明式安全 + 低运行成本"的组合，代价前置在开发阶段而非运行阶段。
- **适用场景**：需要"证明式"安全边界、多语言支持、且能接受生成代码需要编译这一额外步骤的场景。是 Serverless/边缘计算和插件系统（如 Shopify Functions、Envoy 的 WASM 插件）的主流选择。
- **Hosta / hoya 现状**：
  - Hosta：`executor.ts` 中 `WebAssembly.instantiate` + `WebAssembly.promising`（JSPI），host imports 仅 `fetch/log/now/get_input/get_datasource`，符合能力模型（见 RFC 0002 §3、§4.2）。
  - hoya：`execute_wasm`（[`src/wasm_engine/mod.rs`](../../hoya/src/wasm_engine/mod.rs)）用 `wasmtime::{Engine, Store, Linker}`，同样通过 `linker.instantiate` 显式注册宿主函数，架构上是同一思路的 Rust 原生实现，比 Node 内置 `WebAssembly` 多了 `fuel`/内存限额等可配置的资源治理能力（当前代码未见启用，是可优化点）。

### 3.5 OS 级容器隔离（④ 级）

**代表**：Docker（默认 runc）、gVisor（`runsc`，用户态内核拦截 syscall）、Kata Containers（每容器一个轻量 VM）、nsjail/bubblewrap（更轻量的 namespace+seccomp 封装，常见于 OJ/判题系统，如 Judge0）。

- **原理**：利用 Linux namespace（PID/NET/MNT/UTS）+ cgroup（CPU/内存/IO 限额）+ seccomp-bpf（系统调用过滤）构建隔离环境。gVisor 更进一步，在用户态实现了一个部分 Linux 内核（Sentry），代理所有 syscall，减少不受信任代码直接触达宿主内核的机会（微软/Google 内部对 runc vs gVisor 的定性是"gVisor 牺牲部分性能换取更强隔离，弥补容器逃逸风险"）。
- **优点**：成熟度最高，生态工具链完善（镜像、编排、监控一应俱全）；资源限额（CPU/内存/磁盘 IO/网络带宽）通过 cgroup 原生支持；能跑任意语言/任意二进制，无需编译到特殊字节码。
- **缺点**：冷启动通常在几十到几百毫秒（gVisor/Kata 更慢，因为多一层拦截或多一层虚拟化）；共享宿主内核（runc）意味着内核 0day 可导致逃逸，这也是 gVisor/Kata 存在的原因；资源开销（镜像体积、内存 overhead）比进程内方案高一个数量级。
- **成本**：比①-③高一个数量级——需要镜像仓库、编排系统（K8s/Nomad）等常驻基础设施的运维成本；gVisor 官方基准显示部分 syscall 密集场景有 20%-50%+ 的性能损耗，为达到同等吞吐需要更多机器抵消；云厂商通常按 vCPU·秒/内存·秒计费，容器化常驻服务的账单一般高于同等负载的 Serverless 函数，因为镜像更大、资源预留更多，可以把这部分成本视为"隔离性溢价"。
- **适用场景**：需要运行任意语言/任意依赖（如用户上传的 Python 脚本+ pip 依赖）、执行时长较长（秒级到分钟级）、对隔离要求高于性能要求的平台，如在线 IDE、判题系统、Jupyter-based Code Interpreter。
- **代表落地**：OpenAI Code Interpreter（ChatGPT Advanced Data Analysis）公开资料显示其执行环境是 **Jupyter kernel + 容器化隔离（历史上使用过 gVisor 类似方案）**；Judge0（开源判题引擎）用 `isolate`（基于 cgroup+seccomp 的轻量沙箱，IOI 出品）。

### 3.6 MicroVM 隔离（⑤ 级）

**代表**：Firecracker（AWS 出品，Lambda/Fargate 底层技术）、Cloud Hypervisor、QEMU microvm。

- **原理**：为每次执行启动一个**独立的、极简化的虚拟机**（自己的内核，不与宿主共享），但通过精简设备模型和 KVM 直通把冷启动做到 ~125ms 级别（远快于传统 VM 的秒级）。安全边界等同于"物理机之间的隔离"，即使 VM 内核被攻破也拿不到宿主内核。
- **优点**：目前公认的"不受信任代码执行"最强隔离与性能的平衡点；AWS Lambda 大规模生产验证；天然支持 CPU/内存/网络的硬限额（VM 级别配置）。
- **缺点**：自建门槛高（需要 KVM 支持的宿主机，云上开发环境或 Mac 本地不可用，只能跑在 Linux/KVM 宿主或对应云服务上）；冷启动仍比 Isolate/WASM 慢一个量级（百毫秒 vs 毫秒）；工程与运维复杂度高，一般公司选择"买"而非"造"。
- **成本**：自建成本最高——需要专职的虚拟化/内核工程师团队加 KVM 宿主机队列，只有 AWS/Fly.io 这类基础设施公司才自建到生产级别；对绝大多数团队而言更划算的路径是直接采购 Sandbox-as-a-Service（见下），按"沙箱创建次数 + 运行时长（CPU 秒/内存 GB·秒）"计费，单价通常高于自建容器（叠加了厂商毛利），但省去运维人力和试错时间，是"用钱换工程时间"的典型场景。
- **适用场景**：多租户 SaaS 平台执行任意用户/LLM 生成代码，且需要对外提供 SLA 级别隔离保证的场景。
- **代表落地/商业化封装**（"Sandbox-as-a-Service"，本质是把 ④/⑤ 级能力做成 API）：
  - **E2B**：专为 AI Agent/LLM 代码执行设计的沙箱云服务，底层是 Firecracker microVM，提供 Python/JS SDK，秒级创建、支持长时会话与文件系统持久化。
  - **Daytona**：面向 AI 生成代码执行的开发环境沙箱平台，同样基于容器/microVM，强调极速创建（宣称 <100ms 级别）与预热池（warm pool）策略。
  - **Modal Sandboxes**：基于 Modal 自家容器编排系统的按需沙箱，主打细粒度资源计费与快速扩缩容。
  - **Vercel Sandbox / Cloudflare Sandbox SDK**：分别基于各自的 Firecracker（Vercel，复用 AWS Lambda 底座）和容器（Cloudflare，基于其 Workers/Containers 产品）能力，面向"在应用里跑一段 AI 生成代码"的场景做了 SDK 封装。
  - **Riza**：专注"极简 API 调用即可执行代码"的沙箱服务，定位是给 Agent 框架（LangChain 等）用的代码执行工具。
  - 这一类的共性是：**把"不受信任代码执行"整体外包给专业沙箱厂商**，业务方只需调用 HTTP/SDK API，不用自己运维隔离基础设施，代价是网络往返延迟与按量付费成本。
  - **成本**：普遍采用"按沙箱创建次数 + 运行时长（vCPU·秒/内存 GB·秒）+ 出网流量"的组合计费，部分厂商（如 Daytona）主打预热池降低冷启动但会占用一部分常驻资源产生基础费用。相比自建 Firecracker 集群，单位调用成本更高，但免去了虚拟化/内核工程师团队的固定人力成本，对中小团队和早期产品是更低总拥有成本（TCO）的选择；调用量到达一定规模后，自建通常比长期按量付费更划算，这也是多数团队"先买后建"的迁移路径。

### 3.7 Agent/LLM 工具调用层面的沙箱（跨层，架构模式而非单一技术）

- **Anthropic Claude "code execution tool"**：官方将代码执行作为一种 Tool，服务端在托管的容器化沙箱中运行 Bash/Python，模型只拿到 stdout/文件产物，无法直接触达宿主。
- **OpenAI Assistants/Responses API 的 Code Interpreter 工具**：同样是"模型描述意图 → 平台在托管沙箱里执行 → 只把结构化结果回传给模型"，模型本身不直接持有沙箱的网络/文件权限。
- **成本**：这类沙箱能力通常**捆绑在模型 API 调用价格里**（按 token + 沙箱运行时长的组合计费，往往不单列价目），对使用方而言是一种"隐性成本"——难以像独立 Sandbox-as-a-Service 那样单独核算和优化，换来的是无需自建/自选沙箱基础设施的集成简便性。
- 这一层的共同设计模式是：**沙箱是能力的边界，也是"LLM 幻觉/被注入攻击"的边界**——即便 Prompt Injection 诱导模型"生成删除数据的代码"，只要沙箱本身权限设计正确（无价值数据、无持久凭据、出网白名单），损失面也被限定在沙箱内。这与 Hosta 的 JSON 信封 + 显式 host 能力清单思路是一致的。

### 3.8 中国大陆厂商与开源方案

业界综述中提到的 E2B/Daytona/Modal/Riza 等 Sandbox-as-a-Service 以海外厂商为主，但中国大陆的云厂商和开源社区近两年也在快速跟进"面向 AI Agent 的沙箱基础设施"这一方向，且路线和成本模型各有侧重（以下信息基于 2026 年 8 月的公开产品页/仓库信息整理，具体条款以官方最新文档为准）：

- **阿里云无影 AgentBay**（④/⑤ 级，商业化 Sandbox-as-a-Service）：阿里云"无影"团队推出的 AI Agent 云端执行基础设施，以 Sandbox 为核心载体，统一 Session 抽象覆盖浏览器自动化、代码执行、桌面操控、移动应用自动化等场景，支持 SDK 与 MCP（Model Context Protocol）两种接入方式，SDK 已在 GitHub 开源（`aliyun/wuying-agentbay-sdk`）。
  - **隔离与安全**：官方资料强调会话级资源隔离（进程级隔离 + 独立 VPC）、Skill 上架安全审查、运行时行为治理（对死循环/目标偏移等异常自动拦截），定位与 E2B/Daytona 相近，但更强调国内合规诉求（国密 KMS 加密、操作审计留痕）。
  - **成本**：采用"基础权益包（免费）+订阅权益包（包月 Pro/Ultra 档，含赠送积分额度）+ 后付费（超出后按积分/实际资源用量扣费）"的组合计费，积分按不同环境类型（浏览器/代码/桌面/移动）分别设定扣除比例；新用户有 0.01 元体验价。整体计费颗粒度类似"按需 Serverless"，无需承担自建 microVM 集群的固定成本。
- **火山引擎（字节跳动）云沙箱服务**（依托 veFaaS 函数服务，④/⑤ 级）：官方宣称 40ms 预热、100ms 冷启、12 万沙箱/分钟级拉起能力，经"豆包""飞书"等亿级 DAU 场景验证，面向 RL 强化学习（并发运行奖励函数）、Vibe Coding（AI 生成代码的运行时）、Deep Research（工具执行环境）、Computer Use（桌面沙箱）等场景设计。
  - **成本**：按需启停 + 毫秒级精准计费，闲置资源不产生费用；官方宣称相比传统方案可将整体成本降低约 80%（营销数据，需结合自身负载复测），计费逻辑与函数计算类似——只对实际执行时长和资源用量付费，适合调用量波动大、需要极致弹性的 Agent workload。
- **字节跳动 SandboxFusion**（开源，② 级为主，容器化封装）：字节跳动 Seed 团队开源的"面向 LLM 生成代码的安全沙箱"（`bytedance/SandboxFusion`），基于 Docker 提供 20+ 语言运行时（Python/C++/Go/Java/Rust/CUDA 等）与 Jupyter kernel 模式，并内置 HumanEval/MBPP/CodeContests 等评测数据集的 Online Judge 实现，主要用于模型训练/评测流水线中的代码执行与打分，而非面向终端用户的在线服务。
  - **成本**：Apache-2.0 协议、零许可费用，需要自建 Docker 主机；实际成本等于自有服务器/云主机的 CPU 时间 + 运维人力，没有现成的弹性伸缩/多租户配额能力（需要自己在其外层包一层调度），适合已有工程团队、追求完全可控评测环境的场景。
- **Dify-sandbox**（开源，LangGenius 团队，① / ② 级）：Dify 工作流引擎的代码执行节点使用的沙箱组件，Go 编写，基于 Linux seccomp 系统调用白名单 + namespace 隔离，专为"同一进程池里跑多个租户的短代码片段"设计。
  - **成本**：Apache-2.0 协议、零许可费用，部署形态是一个独立 Docker 容器/二进制，运行成本等于宿主机资源；相比 SandboxFusion 更轻量（无需为每种语言单独打镜像），但弹性伸缩、多租户配额同样需要使用方自行在 K8s/网关层实现。
- **蚂蚁集团 Occlum**（开源，另一条技术路线：TEE 机密计算，可视为⑥级"硬件级隔离"）：基于 Intel SGX 的内存安全 LibOS，让未经修改（或少量修改）的程序运行在 SGX Enclave 内，即使宿主 OS/Hypervisor 被攻破，Enclave 内的代码和数据也不会泄露——这是与①-⑤级"信任宿主内核/虚拟化层"完全不同的信任模型（不信任宿主，只信任 CPU 硬件）。
  - **成本**：门槛与成本都是几类方案里最高的——需要支持 SGX/机密计算的实例（阿里云/Azure 机密计算实例的价格通常比同规格普通实例高 20%-50%），且应用需要适配 Occlum 的 LibOS 运行时；由于性能开销和硬件依赖较重，目前更多用于金融、隐私计算等对"防云服务商本身"有强诉求的场景，而非通用的 Agent 代码执行。
- **腾讯云**：截至本次调研，未检索到腾讯云对外发布与阿里云无影 AgentBay、火山引擎云沙箱服务对标的独立 "Agent Sandbox" 产品；可基于云函数 SCF（按调用次数 + 资源时长 + 出网流量计费）或云托管 CloudBase Run（容器常驻、按量计费）自行搭建沙箱层，成本模型与通用 Serverless/容器服务一致，没有面向"不受信任代码执行"的专项定价或安全加固包。若后续腾讯云推出对应产品，应在本 RFC 中补充。

## 5. Hosta 当前方案定位

### 5.1 现状小结

| 运行时                                  | 技术                                                  | 所属层级 | 备注                                                                                |
| --------------------------------------- | ----------------------------------------------------- | -------- | ----------------------------------------------------------------------------------- |
| JavaScript                              | `vm.createContext` + 正则黑名单                       | ①        | `validator.ts` 的黑名单是纵深防御的一环，但不构成真实安全边界                       |
| WASM                                    | `WebAssembly.instantiate` + JSPI，host imports 白名单 | ③        | 能力模型天然安全，但无 CPU/内存硬限额，仅有 3000ms wall-clock 超时（`executor.ts`） |
| hoya（关联项目，尚未接入 Hosta 主流程） | rquickjs（JS，② 级）+ Wasmtime（WASM，③ 级）          | ②/③      | 比 Node `vm` 更彻底的语言层隔离，但同样进程内、无 cgroup 级资源限额                 |

### 5.2 这个选择是否合理

对照 RFC 0001/0002 的产品定位——**单用户本地优先、MVP 阶段、不追求首版多租户**——当前方案是合理的成本/安全取舍：

- 代码在执行前已经过 LLM 生成 + 用户在编辑器里可见/可编辑，不是"匿名公网用户直接注入任意代码"的场景，威胁模型强度低于面向公众的 Sandbox-as-a-Service。
- 单进程零依赖部署是 RFC 0002 明确的架构目标，引入容器/microVM 会直接违背"极简部署"这一约束。
- WASM 路径已经是能力模型（③ 级），是当前技术栈里能拿到的最强隔离，且已经用于计划中的"更受信任的服务端逻辑"场景。

### 5.3 已知差距（风险登记，不代表本 RFC 要求立即修复）

1. `vm.createContext` 官方文档明确写明它不是安全机制；`validator.ts` 的正则黑名单可被已知手法绕过（如 `this.constructor.constructor("return process")()` 之类的原型链逃逸变体）。
2. JS/WASM 执行都与主 Node 进程共享地址空间和事件循环；没有 cgroup 级 CPU/内存限额，恶意或低质量生成代码（死循环、内存膨胀）目前只靠 3000ms 超时兜底，内存膨胀无兜底。
3. 没有针对"多个应用并发执行"场景的资源隔离/配额，一个 Run 理论上可以耗尽整个进程内存影响所有租户（当前单用户场景下影响有限）。
4. `ctx.fetch` 的出网控制是应用层实现（`wasm-bridge.ts` 校验 URL/host），不是网络 namespace 级别的强制隔离，安全性依赖代码本身没有 bug。

### 5.4 建议的演进路径（分阶段，供未来规划参考）

- **当前 MVP 阶段**：维持现状，不建议引入容器/VM——收益（安全性提升）小于成本（架构复杂度、部署门槛提升），且不符合当前威胁模型。
- **若 hoya 接入 Hosta 主流程替代/补充 `vm.createContext`**：优先事项是把 JS 执行也切到能力模型（rquickjs 嵌入解释器，② 级），比继续在 `vm.createContext` 上加黑名单规则性价比更高，同时应补充 Wasmtime 侧的 `fuel`/内存 page 限额配置，把 hoya 的资源治理能力用起来。
- **若产品走向 RFC 0005 描述的多租户 SaaS 愿景**：需要重新评估威胁模型（匿名/半信任用户能直接触发代码执行），届时应在 ④/⑤ 级方案中选型——优先考虑**采购 Sandbox-as-a-Service**以降低自建 microVM 的运维门槛，或自建 gVisor/Firecracker 方案（如果执行量大到自建更划算）。由于 Hosta 面向的是中国大陆用户，若走这条路径，**阿里云无影 AgentBay、火山引擎云沙箱服务**是比 E2B/Daytona 更贴近本地合规（数据不出境、国密加密）与计费习惯（按量/积分计费，避免海外结算）的候选，可与海外厂商一并纳入选型对比；若倾向自建以控制长期成本，字节跳动开源的 SandboxFusion、LangGenius 的 Dify-sandbox 都是可直接复用的开源方案，能省去从零实现 seccomp/命名空间隔离的工程量。这一决策应等有真实多租户流量预测后再触发新的 RFC，不在本次调研范围内提前拍板。

## 6. 结论

业界"运行不受信任代码"的方案本质上是在**隔离强度**与**冷启动/资源成本**之间做权衡，从语言层黑名单到 MicroVM 大致构成一条连续的谱系，近年新出现的 E2B/Daytona/Modal/Riza 等"Sandbox-as-a-Service"是把④/⑤级能力产品化、按需付费的趋势，中国大陆的阿里云无影 AgentBay、火山引擎云沙箱服务是这一趋势在国内的对应产品，字节跳动 SandboxFusion、LangGenius Dify-sandbox 则是可自建的开源选项，蚂蚁 Occlum 代表了另一条以硬件可信执行环境（TEE）为信任根的技术路线。成本层面，隔离越强、通常自建门槛和运行时账单也越高，多数团队的现实路径是"先用嵌入式解释器/WASM 把成本控制住，等真实多租户规模出现后再采购或自建更重的隔离层"，而非一步到位选最强方案。Hosta 当前基于 `vm.createContext`（① 级）+ WASM/JSPI（③ 级）的组合，是与其"单用户本地 MVP"定位相匹配的合理选择，且边际成本几乎为零；`hoya` 项目采用的 QuickJS（② 级）+ Wasmtime（③ 级）代表了一条更彻底的进程内隔离路线，是后续如果要收紧 JS 侧安全边界时的现成候选，而非推翻现有架构。真正需要引入 ④/⑤ 级或外包 Sandbox-as-a-Service（无论海外还是大陆厂商）的临界点，是产品从"单用户工具"转向"多租户对外服务"的那一刻。
